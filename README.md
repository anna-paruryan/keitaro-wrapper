# Keitaro wrapper

Небольшое веб-приложение поверх рекламного трекера [Keitaro](https://keitaro.io), которое работает через его Admin API. Тестовое задание «Обёртка над Keitaro».

Что оно умеет:

* **Создание кампании.** Название, гео (одна или несколько стран) и оффер из поиска с автодополнением. В Keitaro появляется кампания с двумя потоками: первый пропускает посетителей из указанных стран и перенаправляет их на Google, второй отправляет всех остальных на выбранный оффер.
* **Редактор существующей кампании.** Показывает потоки и офферы с долями трафика. Офферы можно добавлять, убирать, возвращать и закреплять (Pin). Изменения копятся в черновике и попадают в Keitaro только по кнопке **Push to KT**. Доли пересчитываются сами и всегда дают ровно 100%.
  Названия кампаний автоматически получают префикс `test_paruryan_`, а редактор разрешает менять только кампании с этим префиксом, чтобы в общем трекере случайно не задеть чужие.

## Быстрый старт

Нужны: Python 3.10+, Node.js 20.19+ (или 22.12+) и [pnpm](https://pnpm.io).

### 1. Бэкенд

Все команды выполняются в папке `backend/`.

```bash
cd backend
 
python -m venv .venv
source .venv/bin/activate              # Windows: .venv\Scripts\activate
pip install -r requirements.txt
 
cp .env.example .env                   # Windows: copy .env.example .env
# открой .env и впиши KEITARO_API_KEY (остальное можно оставить)
 
alembic upgrade head                   # создаёт таблицы в БД (миграции)
uvicorn app.main:app --reload          # запуск на http://127.0.0.1:8000
```

Swagger с описанием всех методов: <http://127.0.0.1:8000/docs>. Корневой адрес `/` ничего не отдаёт, интерфейс живёт во фронтенде.

Ключ Admin API берётся в админке Keitaro: Профиль → API ключи. Ключ хранится только в `backend/.env`. Файл `.env` в `.gitignore`, в репозиторий попадает только образец `.env.example`.

Перед первым запуском можно проверить доступ к трекеру. Скрипт только читает данные и ничего не создаёт:

```bash
python scripts/check_keitaro.py
```

### 2. Фронтенд

Во втором терминале:

```bash
cd client
pnpm install
pnpm dev
```

Открой <http://localhost:5173>. Запросы на `/api` Vite пересылает на бэкенд (`127.0.0.1:8000`), поэтому бэкенд должен быть запущен. Если он не запущен, интерфейс покажет ошибку «502».

## Настройки (`backend/.env`)

| Переменная | По умолчанию | Описание |
|---|---|---|
| `KEITARO_URL` | | адрес трекера, например `https://tlgk.host` (`/admin` на конце можно оставить) |
| `KEITARO_API_KEY` | | ключ Admin API |
| `CAMPAIGN_PREFIX` | пусто | префикс названий (`test_paruryan_`), добавляется автоматически и один раз |
| `KEITARO_GROUP_NAME` | `FORTESTS` | группа кампаний по умолчанию (поиск по названию). Если такой нет, выбирается другая доступная, а причина показывается в форме |
| `KEITARO_SOURCE_NAME` | `FORTESTS` | источник трафика по умолчанию, поиск по названию |
| `KEITARO_DOMAIN` | пусто | часть названия домена; если пусто, берётся первый из API |
| `GOOGLE_REDIRECT_URL` | `https://www.google.com` | куда ведёт первый поток |
| `DATABASE_URL` | `sqlite:///./data/app.db` | база приложения |
| `OFFERS_CACHE_TTL` | `300` | сколько секунд кэшировать список офферов для автодополнения |
| `COUNTRY_FILTER_NAME` | пусто | имя фильтра по стране; по умолчанию определяется через API |

## Как пользоваться

### Создание кампании (вкладка Create campaign)

1. Введи название, например `camp1`. Под полем видно итоговое имя в Keitaro: `test_paruryan_camp1`.
2. Введи гео двухбуквенными кодами через запятую: `MX,AU,RO`.
3. В поле Offer введи ID или часть названия и **выбери оффер из выпадающего списка**. Пока оффер не выбран, кнопка Create неактивна.
4. Нажми Create. Появится карточка с ID кампании и двух потоков.
   Название нельзя использовать повторно, даже если кампанию удалили: Keitaro хранит имена архивных кампаний. В этом случае приложение покажет понятную ошибку, нужно взять другое название.

### Редактор (вкладка Editor)

1. Выбери свою кампанию в списке My campaigns или введи её ID и нажми **Fetch Streams**. Данные читаются из Keitaro, сам Keitaro при этом не меняется.
2. Для каждого потока показаны офферы и их доли. Поток без офферов (редирект на Google) просто отображается и не редактируется.
3. Правки:
    * **Add**: поиск оффера под таблицей, клик по результату добавляет его. Доли делятся поровну.
    * **Remove**: оффер становится серым, доля 0%, остальные пересчитываются.
    * **Bring Back**: возвращает серый оффер.
    * **Pin**: закрепляет текущую долю оффера, при следующих правках она не меняется.
4. Любая правка делает карточку потока жёлтой («Unpublished»). Это значит, что в Keitaro изменений ещё нет.
5. **Push to KT** отправляет поток в Keitaro и карточка снова становится белой. **Cancel** отбрасывает все неопубликованные правки.
6. Состояние хранится в базе, поэтому после обновления страницы (F5) жёлтые потоки остаются жёлтыми.
   Значение цветов:

| Вид | Значение |
|---|---|
| Белая карточка | в карточке то же, что и в Keitaro |
| Жёлтая карточка, тег Unpublished | есть правки, которых в Keitaro ещё нет |
| Строка с тегом `new` | оффер добавлен, в Keitaro его ещё нет |
| Серая зачёркнутая строка, тег `removed` | оффер убран; он остаётся в архиве и его можно вернуть |

Если оффер удалили или выключили в самом Keitaro, то после следующего Fetch он тоже показывается серым с кнопкой Bring Back.

## Логика редактора

| Действие | Что происходит |
|---|---|
| Fetch | потоки и офферы читаются из Keitaro и сверяются с базой. В Keitaro ничего не пишется |
| Add | оффер добавляется в черновик, доли пересчитываются |
| Remove | строка серая, доля 0%, остальные доли пересчитываются |
| Bring Back | серый оффер возвращается в черновик |
| Pin | закрепляет долю, сам по себе ничего не пересчитывает |
| Push to KT | единственное место, где пишем в Keitaro: отправляется весь поток с итоговым списком офферов |
| Cancel | добавленные офферы удаляются из черновика, убранные возвращаются, доли как в Keitaro |

Правила долей (`backend/app/shares.py`, функция `distribute`):

* доли целые, сумма ровно 100 (метод наибольшего остатка);
* закреплённые доли стоят на месте, остальные офферы делят остаток поровну;
* пример: четыре оффера по 25%, закрепили один и убрали другой. Остальные два делят 75%: получается 38% и 37%;
* если закреплённые доли не оставляют места другим офферам, правка отклоняется с понятным сообщением, ничего не меняется.
  Защиты:

* меняются только кампании с префиксом `CAMPAIGN_PREFIX`;
* Push не отправляется, если после последнего Fetch состав офферов в Keitaro изменили вручную. Нужно сделать Fetch заново, иначе можно перезаписать чужие правки;
* поток нельзя опубликовать без активных офферов или если доли не дают 100;
* каждый Push записывается в журнал (`offer_changes`, метод `GET /api/campaigns/{id}/changes`).
## База данных и миграции

Таблицы: `campaigns` (история созданных кампаний), `streams` и `stream_offers` (черновики редактора), `offer_changes` (журнал Push). Схемой управляет Alembic, `create_all` в приложении не используется. Все команды выполняются в `backend/`:

```bash
alembic upgrade head                              # применить все миграции
alembic downgrade -1                              # откатить последнюю
alembic revision --autogenerate -m "описание"     # новая миграция после правки app/models.py
alembic current                                   # текущая версия схемы
```

Файл SQLite (`backend/data/app.db`) создаётся сам. Если забыть применить миграции, при старте бэкенд напишет подсказку в лог.

PostgreSQL:

```bash
pip install "psycopg[binary]"
# в backend/.env:
# DATABASE_URL=postgresql+psycopg://user:password@localhost:5432/keitaro_tools
alembic upgrade head
```

## API

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/health` | сервер жив, настроен ли Keitaro |
| GET | `/api/meta` | префикс, домены, группы, источники и значения по умолчанию |
| GET | `/api/offers?q=&limit=` | поиск офферов по ID или названию |
| POST | `/api/campaigns` | создать кампанию `{name, geo, offer_id}` |
| GET | `/api/campaigns?q=&mine=` | список кампаний (`mine=true` только с нашим префиксом) |
| POST | `/api/campaigns/{id}/fetch` | Fetch Streams |
| GET | `/api/campaigns/{id}/streams` | потоки и черновики из нашей базы (без запроса в Keitaro) |
| POST | `/api/streams/{stream_id}/offers` | Add `{offer_id}` |
| POST | `/api/streams/{stream_id}/offers/{offer_id}/remove` | Remove |
| POST | `/api/streams/{stream_id}/offers/{offer_id}/restore` | Bring Back |
| POST | `/api/streams/{stream_id}/offers/{offer_id}/pin` | Pin `{pinned: true\|false}` |
| POST | `/api/streams/{stream_id}/push` | Push to KT |
| POST | `/api/streams/{stream_id}/cancel` | Cancel |
| GET | `/api/campaigns/{id}/changes` | журнал Push |
| GET | `/api/history` | последние созданные кампании |

Ошибки приходят в виде `{"detail": "понятный текст"}`: 422 неверные данные, 404 не найдено, 409 конфликт, 403 чужая кампания, 502 ошибка Keitaro (с его текстом), 503 Keitaro не настроен. Фронтенд показывает этот текст во всплывающем уведомлении.

```bash
cd backend

```

Сейчас 89 тестов. Они не требуют доступа к Keitaro: он заменён эмулятором (`tests/conftest.py`). Покрыто: создание кампании (оба потока, фильтр по гео, откат при ошибке, повторное имя), весь редактор (Fetch, Add, Remove, Bring Back, Pin, Push, Cancel, защиты, серые офферы после правок в Keitaro), расчёт долей, применение миграций с нуля и их совпадение с моделями.

Эмулятор не доказывает, что настоящий Keitaro примет те же запросы, поэтому всё важное дополнительно проверено вручную (см. ниже).

## Проверено вручную на tlgk.host

* Создание кампании через Swagger и через интерфейс: два потока, фильтр по стране, редирект на Google, оффер во втором потоке.
* Fetch: потоки и офферы совпадают с Keitaro, редирект-поток показывается без офферов.
* Add + Push: оффер появляется в потоке Keitaro, доли совпадают с интерфейсом.
* Remove + Push: оффер исчезает из Keitaro, в редакторе остаётся серым. Bring Back + Push возвращает его.
* Оффер, удалённый вручную в Keitaro, после Fetch становится серым; оставшиеся доли показываются так, как они лежат в Keitaro.
* Pin: закреплено 34%, второй оффер убран, оставшийся получает 66%; после Bring Back снова 34 / 33 / 33.
## Допущения и ограничения

* **Домен, группа, источник.** Ключ, с которым разрабатывалось приложение, не видит домен `in.posdk.xyz`, источник и группу `FORTESTS` (в API их нет). Поэтому форма показывает то, что отдаёт API, а причины выводятся в блоке «Why these values?». Кампании создавались с группой из API и без источника, а домен подставил сам Keitaro (домен по умолчанию). Если у другого ключа эти объекты видны, они выбираются автоматически по `KEITARO_*` из `.env`.
* **Нет авторизации.** У API нет логина: любой, кто достучится до порта 8000, действует от имени ключа Keitaro (в рамках префикса). Приложение рассчитано на локальный запуск. Выкладывать бэкенд в открытый интернет без авторизации нельзя.
* **Keitaro не пересчитывает доли сам.** Если убрать оффер вручную в Keitaro, остальные доли остаются как были (сумма может быть не 100). Редактор показывает их как есть и пересчитывает, только когда вы меняете поток.
* **Push отправляет поток целиком.** Берётся текущий поток из Keitaro, в нём заменяется список `offers`, и он отправляется обратно (`PUT /streams/{id}`). Убранный оффер просто пропадает из списка потока.
* **Названия полей Keitaro.** Публичное описание API ([admin-api.docs.keitaro.io](https://admin-api.docs.keitaro.io)) не полностью совпадает с поведением конкретной версии. Всё, что зависит от формата Keitaro, собрано в `backend/app/keitaro.py` и в начале `backend/app/services.py`. `python scripts/check_keitaro.py` показывает реальные ответы трекера.
* **Имя кампании** нельзя использовать повторно, даже после удаления (архив Keitaro).
